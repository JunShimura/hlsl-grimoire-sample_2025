# 行列変換の数式

## 4x4 変換行列の構造

HLSLの`float4x4`行列は見た目上は 4x4 の2次元配列ですが、CPU側（DirectXMath / XMFLOAT4X4）とシェーダ側でのメモリ配置（row-major / column-major）や、アップロード時に行う転置(Transpose)によって、どの要素が"平行移動成分"に相当するかが変わります。以下に両者の関係を整理します。

CPU 側（DirectX の XMFLOAT4X4 / Matrix クラス）は行優先(row-major)表現を用います。通常の表示は次のようになります：

```
（CPU: row-major 表示）
       [列0] [列1] [列2] [列3]
[行0]  m00   m01   m02   m03
[行1]  m10   m11   m12   m13
[行2]  m20   m21   m22   m23
[行3]  m30   m31   m32   m33

この場合、平行移動成分は4行目の先頭に入ることが多く、CPU 側の命名では _41,_42,_43（ここでは m30,m31,m32）になります。
```

一方で、HLSL のデフォルトは列優先(column-major)での最適配置です。多くの実装（DirectXTK 等）では、CPU 側で計算した行列をシェーダに渡す前に XMMatrixTranspose を使って転置してから定数バッファにセットします。転置を行うと、上の行列は次のように入れ替わります：

```
（転置後 = シェーダにアップロードされるレイアウト）
       [列0] [列1] [列2] [列3]
[行0]  m00   m10   m20   m30
[行1]  m01   m11   m21   m31
[行2]  m02   m12   m22   m32
[行3]  m03   m13   m23   m33

この場合、元の CPU 側の4行目にあった平行移動成分(m30,m31,m32)は転置により "4列目" の上三つの要素 (m30,m31,m32) に移動します。
```

## 各成分の役割

```
[  回転・スケール（X軸）  回転・スケール（Y軸）  回転・スケール（Z軸）  平行移動  ]

[ m00  m01  m02  m03 ]  ← X成分の変換係数
[ m10  m11  m12  m13 ]  ← Y成分の変換係数
[ m20  m21  m22  m23 ]  ← Z成分の変換係数
[ m30  m31  m32  m33 ]  ← 平行移動（Translation）+ W成分
   ↑    ↑    ↑    ↑
   X    Y    Z    W
```

### 平行移動成分の取得

注意: シェーダ側でどの要素が"平行移動"を表すかは、CPU 側で転置しているかどうか (XMMatrixTranspose の有無)、およびシェーダ内での行列の解釈 (row_major 指定など) に依存します。間違いを減らすため、実際のコードでは次のいずれかの方法を使うことを推奨します。

- 安全な方法 — 原点を変換して位置を得る:

  ```hlsl
  // 原点(0,0,0,1) を行列で変換するとワールド位置が得られる
  float4 objectPos = mul(mWorld, float4(0,0,0,1));
  float3 worldPos = objectPos.xyz;
  ```

  この方法は行列が転置されているかどうか、row/column の指定がどうなっているかに依らず正しいワールド位置を返します。

- 直接成分を読む場合 — 配置を知っているときの対応表:

  - CPU が row-major（XMFLOAT4X4）のままシェーダに渡している（転置していない）場合:

    m[3][0], m[3][1], m[3][2] が平行移動 (CPU 側でいう _41,_42,_43 に相当)

  - CPU 側で XMMatrixTranspose 等により転置してからアップロードしている場合（DirectXTK の EffectCommon 等が行う挙動）:

    平行移動成分はマトリクスの "4列目" に入るため、HLSL 表記では m._14, m._24, m._34 （または行列を列としてアクセスできる場合は各行の .w 成分）に相当します。

  しかし符号や詳細なメモリ順はプロジェクトの実装（どのタイミングで転置しているか）によって変わるため、上記直接アクセスは注意して使ってください。

## 行列とベクトルの乗算

### 元のベクトル

変換前のベクトルを以下のように定義します：

```
v = (x, y, z, w)
```

### mul(matrix, vector) の場合

HLSLで`mul(mWorld, vsIn.pos)`のように記述した場合、以下の計算が行われます：

```
v' = mWorld × v
```

## 変換後のベクトルの各成分の計算式

### 変換後の x' の計算式

```
x' = m00 * x + m01 * y + m02 * z + m03 * w
```

### 変換後の y' の計算式

```
y' = m10 * x + m11 * y + m12 * z + m13 * w
```

### 変換後の z' の計算式

```
z' = m20 * x + m21 * y + m22 * z + m23 * w
```

### 変換後の w' の計算式

```
w' = m30 * x + m31 * y + m32 * z + m33 * w
```

## 行列形式での表現

```
[x']   [m00  m01  m02  m03]   [x]
[y'] = [m10  m11  m12  m13] × [y]
[z']   [m20  m21  m22  m23]   [z]
[w']   [m30  m31  m32  m33]   [w]
```

## 実際の変換例

### ワールド変換（sample.fxのコード）

```hlsl
psIn.pos = mul(mWorld, vsIn.pos);
```

この変換では：
- vsIn.pos = (x, y, z, 1) ← 頂点座標（wは通常1）
- m00～m22: 回転やスケールの情報

注意点:
- 実装例（DirectXTK 等）では、CPU 側で計算した行列をシェーダに渡す前に XMMatrixTranspose を呼んでから定数バッファへセットすることが多く、その場合は "平行移動成分が行に入る/列に入る" の表記が入れ替わります。上の節で示したように、転置前の CPU 表現では m30,m31,m32 が位置になりますが、転置後はそれらは 4 列目に移動します。

そのため、コード中で平行移動成分を参照するときは、転置の有無に注意するか、mul(mWorld, float4(0,0,0,1)) のように原点を変換して得る方法を使うのが確実です。

具体的には：
```
x' = m00*x + m01*y + m02*z + m03*1
y' = m10*x + m11*y + m12*z + m13*1
z' = m20*x + m21*y + m22*z + m23*1
w' = m30*x + m31*y + m32*z + m33*1
```

### オブジェクト位置の取得（sample.fxのコード）

```hlsl
float4 objectPos = mWorld[3];
```

これは行列の4行目（平行移動成分）を直接取得しています：
```
objectPos = (m30, m31, m32, m33)
```

この値がオブジェクトのワールド座標系での位置を表します。

## C++ 側から HLSL へ行列がどのように渡されるか（本プロジェクトの流れ）

このプロジェクトで mWorld がシェーダに渡される実際の流れを簡潔に示します。実装箇所の参照と要点を下にまとめます。

1) ワールド行列の計算
   - 実装: Model::CalcWorldMatrix (MiniEngine/Model.h / Model.cpp)
   - 内容: 位置(pos), 回転(rot), スケール(scale) から Matrix を合成します。合成順は mBias * mScale * mRot * mTrans です。

2) Draw 呼び出しで渡す
   - 実装: Model::Draw -> MeshParts::Draw (MiniEngine/Model.cpp, MeshParts.cpp)
   - 内容: Model が保持する m_world を MeshParts::Draw に渡します。

3) 定数バッファへコピー（CPU -> GPU）
   - 実装: MeshParts::DrawCommon 内で SConstantBuffer に代入し m_commonConstantBuffer.CopyToVRAM(cb) を呼ぶ (MiniEngine/MeshParts.cpp)
   - 実装: ConstantBuffer::CopyToVRAM はマップ済み領域へメモリコピーを行うだけで、行列の転置は行っていません (MiniEngine/ConstantBuffer.cpp)。

4) CBV（定数バッファビュー）作成とディスクリプタヒープ登録
   - 実装: DescriptorHeap::Commit (MiniEngine/DescriptorHeap.cpp)

5) コマンドリストにディスクリプタヒープをセットして描画
   - 実装: RenderContext::SetDescriptorHeaps / Material::BeginRender など

6) HLSL 側での受け取り
   - 実装: Sample_14_04/Assets/shader/sample.fx
   - 定義: cbuffer ModelCb : register(b0) { float4x4 mWorld; float4x4 mView; float4x4 mProj; }

要点:
- Matrix クラス（MiniEngine/math/Matrix.h）は内部に DirectX::XMFLOAT4X4 mat を持ち、MakeTranslation 等は DirectX::XMStoreFloat4x4 を使って mat に書き込みます。
- Matrix::operator DirectX::XMMATRIX() は XMLoadFloat4x4(&mat) を返すため、XMMATRIX との相互変換は mat の配置に基づき行われます。
- 本プロジェクトでは CPU 側の Matrix（XMFLOAT4X4 相当）のバイト配列をそのまま定数バッファに memcpy しています。つまり CPU 側で明示的に XMMatrixTranspose を呼んで転置しない限り、転置は行われません。
- Matrix のメンバ名と cbuffer 表現の対応例:
  - CPU(Matrix.mat._41) == m[3][0] == 本文中でいう m30 (X 成分)
  - CPU(Matrix.mat._42) == m[3][1] == m31 (Y 成分)
  - CPU(Matrix.mat._43) == m[3][2] == m32 (Z 成分)

推奨される対応:
- 安全策 A（簡単）: シェーダで row_major を明示する
  - 例: cbuffer ModelCb : register(b0) { row_major float4x4 mWorld; row_major float4x4 mView; row_major float4x4 mProj; }
  - 理由: CPU の row-major 表現をそのまま扱える。

- 安全策 B（一般的）: CPU 側で転置してからアップロード
  - 例: auto worldForCB = XMMatrixTranspose(world); コピーは転置済み行列を CB に行う。
  - 理由: HLSL の列優先デフォルトに合わせる方法。

どちらを採るにせよ、平行移動成分を直接参照するコード（例: float4 objectPos = mWorld[3];）は転置の有無で意味が変わるため注意が必要です。転置に依存せず確実にワールド位置を得るには次のように原点を変換してください:

```hlsl
float4 objectPos = mul(mWorld, float4(0,0,0,1)); // 転置の有無に依らず正しいワールド位置を返す
```

実装参照一覧:
- ワールド行列合成: MiniEngine/Model.h (CalcWorldMatrix)
- 定数バッファ代入: MiniEngine/MeshParts.cpp (DrawCommon -> SConstantBuffer)
- 定数バッファコピー: MiniEngine/ConstantBuffer.cpp (CopyToVRAM)
- ディスクリプタヒープ: MiniEngine/DescriptorHeap.cpp (Commit)
- シェーダー: Sample_14_04/Assets/shader/sample.fx (cbuffer ModelCb)
