# シャドウマップで同じ物体が複数のモデルを持つ理由

## 質問

> シャドウマップの描画で、バッファを描画するためにそれぞれでモデルを保持しているが、  
> **同じ物体という状態**は、何故、発生しているのか。

## 回答の要点

**結論**: DirectX 12の**パイプラインステートオブジェクト（PSO）**の仕組み上、**異なるシェーダーや設定で描画するには、別々のモデルインスタンスが必要**だからです。

---

## 詳細な解説

### 1. 現在の実装状況

`ModelRender` クラスは、1つの物体（例：ティーポット）に対して、**複数のモデルインスタンス**を保持しています。

```cpp
class ModelRender
{
private:
	Model m_zprepassModel;                      // 1つ
	Model m_renderToGBufferModel;               // 1つ
	Model m_forwardRenderModel;                 // 1つ
	Model m_shadowModels[4][3];                 // 12個 (4ライト × 3エリア)
	// 合計: 1 + 1 + 1 + 12 = 15個のモデルインスタンス
};
```

**疑問**: なぜ同じティーポットなのに、15個ものモデルが必要なのか？

---

### 2. DirectX 12のパイプラインステートオブジェクト（PSO）

#### PSOとは？

**PSO（Pipeline State Object）** は、DirectX 12 で導入された概念で、描画に必要な**すべての設定をまとめたもの**です。

PSOには以下の情報が含まれます：

```cpp
struct PipelineStateObject {
	シェーダープログラム（頂点シェーダー、ピクセルシェーダー）
	レンダーターゲットのフォーマット（DXGI_FORMAT）
	深度ステンシルのフォーマット
	ブレンドステート（透明度の扱い方）
	ラスタライザーステート（カリング、ワイヤーフレームなど）
	サンプラーステート（テクスチャの補間方法）
	トポロジー（三角形、線など）
	ルートシグネチャ（シェーダーとの入出力契約）
	// ... 他多数
};
```

#### 重要な制約

**DirectX 12では、PSOは描画前に確定している必要があり、描画中に変更できません。**

つまり、**異なるシェーダーや設定で描画するには、別々のPSOが必要**です。

---

### 3. なぜ複数のモデルが必要なのか？

#### 各モデルが使用する異なるPSO

| モデル | シェーダー | レンダーターゲット | 深度バッファ | 用途 |
|--------|-----------|------------------|------------|------|
| `m_shadowModels` | `DrawShadowMap.fx` | R32_FLOAT (深度のみ) | D32_FLOAT | シャドウマップ作成 |
| `m_zprepassModel` | `ZPrepass.fx` | R32G32_FLOAT | D32_FLOAT | 深度事前取得 |
| `m_renderToGBufferModel` | `RenderToGBufferFor3DModel.fx` | 5つのG-Buffer | D32_FLOAT | 色・法線・材質 |
| `m_forwardRenderModel` | ユーザー指定（例: `sample.fx`） | R32G32B32A32_FLOAT | 共有 | 特殊なシェーディング |

**これらは全て異なるPSOを使用します。**

#### コードで見る初期化の違い

```cpp
// シャドウマップ用モデル（DrawShadowMap.fx を使用）
ModelInitData shadowInitData;
shadowInitData.m_fxFilePath = "Assets/shader/preset/DrawShadowMap.fx";
shadowInitData.m_colorBufferFormat[0] = DXGI_FORMAT_R32_FLOAT;  // ← 深度のみ
m_shadowModels[0][0].Init(shadowInitData);

// G-Buffer用モデル（RenderToGBufferFor3DModel.fx を使用）
ModelInitData gBufferInitData;
gBufferInitData.m_fxFilePath = "Assets/shader/preset/RenderToGBufferFor3DModel.fx";
gBufferInitData.m_colorBufferFormat[0] = DXGI_FORMAT_R32G32B32A32_FLOAT;  // ← 色情報
gBufferInitData.m_colorBufferFormat[1] = DXGI_FORMAT_R8G8B8A8_UNORM;      // ← 法線
gBufferInitData.m_colorBufferFormat[2] = DXGI_FORMAT_R32G32B32A32_FLOAT;  // ← 位置
gBufferInitData.m_colorBufferFormat[3] = DXGI_FORMAT_R8G8B8A8_UNORM;      // ← 材質
gBufferInitData.m_colorBufferFormat[4] = DXGI_FORMAT_R8G8B8A8_UNORM;      // ← 影パラメータ
m_renderToGBufferModel.Init(gBufferInitData);
```

**PSOが異なる = 別々のモデルインスタンスが必要**

---

### 4. もし1つのモデルで済ませようとしたら？

#### 代替案1: 描画ごとにシェーダーを切り替える

```cpp
// 理論上のコード（実際には非効率）
Model teapot;
teapot.Init("teapot.tkm");

// シャドウマップ描画
teapot.SetShader("DrawShadowMap.fx");          // ← PSOを変更
teapot.SetRenderTarget(shadowMapRenderTarget); // ← レンダーターゲットを変更
teapot.Draw(rc);

// G-Buffer描画
teapot.SetShader("RenderToGBufferFor3DModel.fx"); // ← PSOを変更
teapot.SetRenderTarget(gBufferRenderTargets);     // ← レンダーターゲットを変更
teapot.Draw(rc);
```

**問題点:**

1. **PSO作成のコストが高い**
   - DirectX 12では、PSO作成は非常に重い処理
   - 毎フレームPSOを作り直すと、フレームレートが大幅に低下

2. **GPU側のパイプライン切り替えコストが高い**
   - シェーダーの切り替えには、GPUの内部状態をリセットする必要がある
   - 頻繁に切り替えると、GPU効率が悪化

3. **コードが複雑になる**
   - どのタイミングでシェーダーを切り替えるか管理が必要
   - バグの温床になりやすい

---

#### 代替案2: Uber Shader（万能シェーダー）

すべての描画パターンに対応した1つの巨大なシェーダーを作成する方法もあります。

```hlsl
// uber_shader.fx（すべての機能を詰め込んだシェーダー）
cbuffer Settings {
	int mode; // 0=シャドウマップ, 1=ZPrepass, 2=G-Buffer, 3=フォワード
};

struct PS_OUTPUT {
	float shadowDepth : SV_Target0;
	float4 albedo : SV_Target1;
	float4 normal : SV_Target2;
	// ... 全てのレンダーターゲット
};

PS_OUTPUT PSMain() {
	PS_OUTPUT output;

	if (mode == 0) {
		// シャドウマップ用の処理
		output.shadowDepth = depth;
	} else if (mode == 1) {
		// ZPrepass用の処理
		// ...
	} else if (mode == 2) {
		// G-Buffer用の処理
		// ...
	} else {
		// フォワードレンダリング用の処理
		// ...
	}

	return output;
}
```

**問題点:**

1. **シェーダーコンパイル時間が長い**
   - すべての機能を含むため、コンパイルに時間がかかる

2. **実行時のパフォーマンス低下**
   - 使わない分岐が多数あり、GPU効率が悪化
   - 命令キャッシュがヒットしにくくなる

3. **メンテナンスが困難**
   - 1つのシェーダーに全機能が詰まるため、バグ修正が大変

---

### 5. 現在の実装方式のメリット

#### メリット1: パフォーマンスが良い

**PSO事前作成 + 専用シェーダー** の組み合わせにより、最高のパフォーマンスを実現します。

```
描画フロー:

1. 初期化時（ゲーム起動時）
   ├─ 各モデル用のPSOを作成（時間がかかってもOK）
   └─ シェーダーをコンパイル

2. 描画時（毎フレーム）
   ├─ シャドウマップ描画: m_shadowModels[i][j].Draw() ← PSO切り替えなし、高速！
   ├─ ZPrepass描画: m_zprepassModel.Draw()             ← PSO切り替えなし、高速！
   ├─ G-Buffer描画: m_renderToGBufferModel.Draw()      ← PSO切り替えなし、高速！
   └─ フォワード描画: m_forwardRenderModel.Draw()       ← PSO切り替えなし、高速！
```

**ポイント**: 描画時には、**事前に作成したPSOを使い回すだけ**なので、非常に高速です。

---

#### メリット2: シェーダーが最適化される

各用途に特化したシェーダーを使うため、無駄な処理がありません。

**シャドウマップ用シェーダー（DrawShadowMap.fx）**
```hlsl
// 深度だけ出力（シンプル！）
float PSMain() : SV_Target0
{
	return input.depth;
}
```

**G-Buffer用シェーダー（RenderToGBufferFor3DModel.fx）**
```hlsl
// 5つの情報を出力（詳細！）
struct PS_OUTPUT {
	float4 albedo       : SV_Target0;
	float4 normal       : SV_Target1;
	float4 worldPos     : SV_Target2;
	float4 metalSmooth  : SV_Target3;
	float4 shadowParam  : SV_Target4;
};
```

**GPU側の最適化**：各シェーダーが単純なので、GPU内での最適化が効きやすい。

---

#### メリット3: コードの保守性が高い

各描画パスが独立しているため、機能追加や修正が容易です。

```cpp
// シャドウマップの処理を変更したい場合
// → m_shadowModels と DrawShadowMap.fx だけ修正すればOK

// G-Bufferの処理を変更したい場合
// → m_renderToGBufferModel と RenderToGBufferFor3DModel.fx だけ修正すればOK
```

他の描画パスに影響を与えないため、安全に変更できます。

---

### 6. デメリット：メモリ使用量の増加

#### メモリ使用量の詳細

1つのモデルインスタンスには、以下のデータが含まれます：

```cpp
class Model {
	VertexBuffer m_vertexBuffer;        // 頂点データ（メッシュ形状）
	IndexBuffer m_indexBuffer;          // インデックスデータ
	ConstantBuffer m_constantBuffer;    // 定数バッファ（行列など）
	Texture* m_textures;                // テクスチャへのポインタ（共有）
	PipelineState m_pipelineState;      // PSO
	// ... 他
};
```

**重要なポイント**：

- **頂点データとインデックスデータは共有されます**（内部で参照カウント管理）
- **テクスチャも共有されます**
- **独立して保持されるのは、PSO と定数バッファ（行列など）のみ**

#### 実際のメモリ増加量

```
ティーポット1つあたり:

【共有されるデータ（1回だけ確保）】
- 頂点データ: 約10KB
- インデックスデータ: 約5KB
- テクスチャ: 約2MB（アルベド、法線、メタリックなど）
合計: 約2.015MB

【各モデルインスタンスごとに必要なデータ（15個分）】
- PSO: 約1KB × 15 = 15KB
- 定数バッファ（行列など）: 約256B × 15 = 3.75KB
合計: 約18.75KB

【総メモリ使用量】
2.015MB + 18.75KB ≈ 2.03MB
```

**結論**: 15個のモデルインスタンスを持っても、**追加のメモリ使用量はわずか約19KB**です。

これは、現代のGPUメモリ（数GB～数十GB）から見ると、**無視できるレベル**です。

### 8. まとめ

#### なぜ複数のモデルが必要なのか？

| 理由 | 説明 |
|------|------|
| **DirectX 12の仕組み** | 異なるPSOで描画するには、別々のモデルインスタンスが必要 |
| **パフォーマンス** | PSO切り替えのコストを避け、高速描画を実現 |
| **最適化** | 各用途に特化したシェーダーで、無駄な処理を削減 |
| **保守性** | 各描画パスが独立し、機能追加や修正が容易 |

#### メモリ使用量は問題ないのか？

| 項目 | 値 |
|------|-----|
| 共有データ（メッシュ、テクスチャ） | 約2.015MB（1回だけ） |
| 追加データ（PSO、定数バッファ） | 約19KB（15個分） |
| **合計** | **約2.03MB** |

**結論**: メモリ増加は微小であり、パフォーマンスのメリットが圧倒的に大きい。

---

#### 代替案との比較

| 方式 | メリット | デメリット |
|------|---------|----------|
| **現在の実装**<br>（複数のモデルインスタンス） | ✅ 最高のパフォーマンス<br>✅ シェーダーが最適化<br>✅ 保守性が高い | ❌ わずかにメモリ使用量増加（約19KB） |
| **1つのモデル + シェーダー切り替え** | ✅ メモリ節約 | ❌ PSO作成コストが高い<br>❌ GPU効率が悪化<br>❌ コードが複雑 |
| **Uber Shader（万能シェーダー）** | ✅ 1つのシェーダーで対応 | ❌ コンパイル時間が長い<br>❌ 実行時パフォーマンス低下<br>❌ メンテナンスが困難 |

## 9. ModelクラスとPSOの関連：実装詳細

ここでは、このエンジンの実装における **Modelクラスの内部構造** と **PSO（パイプラインステートオブジェクト）** の関係、そして **メモリ共有の仕組み** について詳しく解説します。

### 9.1 Modelクラスの構造

```cpp
// Model.h より
class Model {
private:
    bool m_isInited = false;        // 初期化されている？
    Matrix m_world;                 // ワールド行列（各インスタンス独立）
    TkmFile* m_tkmFile;             // tkmファイルへのポインタ（共有）
    Skeleton m_skeleton;            // スケルトン（各インスタンス独立）
    MeshParts m_meshParts;          // メッシュパーツ（PSO保持）
    EnModelUpAxis m_modelUpAxis;    // モデルの上方向
};
```

#### 各メンバの役割

| メンバ変数 | 役割 | 共有/独立 |
|-----------|------|----------|
| `m_world` | ワールド行列（位置・回転・拡大率） | **独立**（各モデルで異なる位置に配置可能） |
| `m_tkmFile` | メッシュデータ（頂点・インデックス）へのポインタ | **共有**（同じファイルを参照） |
| `m_skeleton` | ボーンアニメーション用のスケルトン | **独立**（各モデルで異なるポーズ可能） |
| `m_meshParts` | **PSO**とマテリアルを保持 | **独立**（異なるシェーダー/設定） |
| `m_modelUpAxis` | モデルの上方向（Y-up or Z-up） | 独立 |

---

### 9.2 TkmFileのリソースバンク（メモリ共有の仕組み）

#### TResourceBankテンプレートクラス

このエンジンでは、`TResourceBank` というテンプレートクラスで、**リソースの共有管理** を実現しています。

```cpp
// TResourceBank.h
template<class TResource>
class TResourceBank {
public:
    TResource* Get(const char* filePath)
    {
        auto it = m_resourceMap.find(filePath);
        if (it != m_resourceMap.end()) {
            return it->second.get();  // 既に登録済みなら、そのポインタを返す
        }
        return nullptr;  // 未登録ならnullptrを返す
    }

    void Regist(const char* filePath, TResource* resource)
    {
        auto it = m_resourceMap.find(filePath);
        if (it == m_resourceMap.end()) {
            // まだ登録されていなければ、新規登録
            m_resourceMap.insert(
                std::pair<std::string, TResourcePtr>(filePath, resource)
            );
        }
    }

private:
    using TResourcePtr = std::unique_ptr<TResource>;
    std::map<std::string, TResourcePtr> m_resourceMap;  // ファイルパスをキーとしたマップ
};
```

**ポイント**:
- `std::unique_ptr` で管理しているため、**自動的にメモリ解放**される
- `std::map` でファイルパスをキーとして管理
- **同じファイルパスなら、同じリソースを返す**

---

#### Model::Init()でのTkmFile取得

```cpp
// Model.cpp の Init() より
void Model::Init(const ModelInitData& initData)
{
    // ... 省略 ...

    // TkmFileをバンクから取得（既に登録済みなら、それを使用）
    auto tkmFile = g_engine->GetTkmFileFromBank(initData.m_tkmFilePath);

    if (tkmFile == nullptr) {
        // 未登録の場合は、新規にロードしてバンクに登録
        tkmFile = new TkmFile;
        tkmFile->Load(initData.m_tkmFilePath);  // ファイルからロード
        g_engine->RegistTkmFileToBank(initData.m_tkmFilePath, tkmFile);
    }

    // このモデルインスタンスは、共有されたTkmFileへのポインタを保持
    m_tkmFile = tkmFile;

    // MeshPartsを初期化（ここでPSOが作成される）
    m_meshParts.InitFromTkmFile(
        *m_tkmFile,
        initData.m_fxFilePath,           // シェーダーファイルパス
        initData.m_vsEntryPointFunc,     // 頂点シェーダーのエントリーポイント
        initData.m_psEntryPointFunc,     // ピクセルシェーダーのエントリーポイント
        initData.m_colorBufferFormat,    // レンダーターゲットのフォーマット
        // ... 省略 ...
    );

    // ... 省略 ...
}
```

#### メモリ共有の流れ

```
【1回目のモデル初期化】
Model #1 (シャドウマップ用)
    ↓
    TkmFile "teapot.tkm" をロード → バンクに登録
    ├─ 頂点データ: 10KB
    ├─ インデックスデータ: 5KB
    └─ マテリアル情報: 1KB

    m_tkmFile = バンクから取得したポインタ（共有）
    m_meshParts = 新規作成（PSO: DrawShadowMap.fx）


【2回目のモデル初期化】
Model #2 (ZPrepass用)
    ↓
    TkmFile "teapot.tkm" をバンクから取得
    （既に登録済みなので、新規ロードしない）

    m_tkmFile = バンクから取得したポインタ（共有） ← Model #1 と同じポインタ！
    m_meshParts = 新規作成（PSO: ZPrepass.fx）     ← 異なるPSO


【3回目のモデル初期化】
Model #3 (G-Buffer用)
    ↓
    TkmFile "teapot.tkm" をバンクから取得
    （既に登録済みなので、新規ロードしない）

    m_tkmFile = バンクから取得したポインタ（共有） ← Model #1, #2 と同じポインタ！
    m_meshParts = 新規作成（PSO: RenderToGBufferFor3DModel.fx） ← 異なるPSO


... 以下、15個すべてのモデルで同様
```

**結論**: **頂点データとインデックスデータは、メモリ空間で完全に共有**されています！

### 9.3 MeshPartsとPSOの関係

#### MeshParts クラスの構造

```cpp

struct SMesh {

    std::vector<Material*> m_materials;       // マテリアル（PSO保持）
    // ...
};

class MeshParts {
private:
    std::vector<SMesh*> m_meshs;             // メッシュの配列
    DescriptorHeap m_descriptorHeap;         // ディスクリプタヒープ
    // ...
};
```

#### Materialクラスが PSO を保持

```cpp
// Material.h より（簡略版）
class Material {
private:
    PipelineState m_pipelineState;           // PSO（重要！）

    ConstantBuffer m_constantBuffer;         // 定数バッファ
    // ...

```

**ポイント**: 各 `Material` が **独自のPSO** を保持します。

---

#### 頂点バッファの初期化（VertexBuffer）

```cpp
// MeshParts.cpp の InitFromTkmFile() より（推測）
void MeshParts::InitFromTkmFile(const TkmFile& tkmFile, ...)
{
    // TkmFile から頂点データを取得
    const auto& meshData = tkmFile.GetMesh(0);

    // 頂点バッファを作成（GPU上にメモリを確保）
    m_meshs[0]->m_vertexBuffer.Init(
        meshData.vertices,      // CPU側の頂点データ（TkmFileから取得）
        meshData.vertexCount
    );

    // インデックスバッファを作成
    m_meshs[0]->m_indexBufferArray[0]->Init(
        meshData.indices,       // CPU側のインデックスデータ（TkmFileから取得）
        meshData.indexCount
    );

    // マテリアルを作成（ここでPSOが作成される）
    m_meshs[0]->m_materials[0]->InitFromShadowMap(
        fxFilePath,             // "DrawShadowMap.fx"
        vsEntryPointFunc,       // "VSMain"
        psEntryPointFunc,       // "PSMain"
        colorBufferFormat       // DXGI_FORMAT_R32_FLOAT
    );
}
```

#### 頂点バッファの実体はどこにあるのか？

**頂点バッファの実体は GPU上のメモリ** にあります。

```
CPU側（メインメモリ）
    TkmFile "teapot.tkm"
        ├─ 頂点データ（10KB）      ← バンクで共有
        ├─ インデックスデータ（5KB） ← バンクで共有
        └─ マテリアル情報（1KB）
            ↓
            ↓ GPU に転送（Model::Init() 時に1回だけ）
            ↓
GPU側（ビデオメモリ）
    VertexBuffer
        ├─ 頂点データ（10KB） ← 全モデルで同じ GPU リソースを参照？

    いいえ、実は...
```

#### 重要な実装の詳細

実際には、**各モデルインスタンスが独自の VertexBuffer オブジェクトを作成**しますが、内部的には **同じGPUリソース（ID3D12Resource）を参照** する可能性があります。

ただし、このエンジンの実装では、**各モデルが独立した VertexBuffer を作成**しているため、以下のようになります：

```
Model #1 (シャドウマップ用)
    m_tkmFile → 共有されたTkmFile
    m_meshParts.m_meshs[0].m_vertexBuffer → GPU上の VertexBuffer #1

Model #2 (ZPrepass用)
    m_tkmFile → 共有されたTkmFile（Model #1 と同じ）
    m_meshParts.m_meshs[0].m_vertexBuffer → GPU上の VertexBuffer #2

... 以下同様
```

**問題点**: この実装では、頂点データが **GPU上で重複** しています！

---

### 9.4 メモリ使用量の正確な内訳

#### CPU側（メインメモリ）

```
【共有データ】
TkmFile "teapot.tkm"（バンクで管理）
    ├─ 頂点データ: 10KB  ← 1回だけ確保
    ├─ インデックスデータ: 5KB  ← 1回だけ確保
    └─ マテリアル情報: 1KB
    合計: 16KB

【各モデルインスタンスごと（15個）】
Model インスタンス
    ├─ m_world（Matrix）: 64B
    ├─ m_tkmFile（ポインタ）: 8B
    ├─ m_skeleton: 約1KB（アニメーションありの場合）
    └─ m_meshParts: 約16B（ポインタなど）
    合計: 約1.1KB × 15 = 約16.5KB
```

**CPU側の総メモリ使用量**: 16KB + 16.5KB = **約32.5KB**

---

#### GPU側（ビデオメモリ）

```
【頂点データ（重複あり）】
VertexBuffer × 15個
    ├─ 各10KB × 15 = 150KB  ← 重複している！

【インデックスデータ（重複あり）】
IndexBuffer × 15個
    ├─ 各5KB × 15 = 75KB   ← 重複している！

【テクスチャ（共有）】
Texture（アルベド、法線、メタリックなど）
    ├─ 約2MB × 1 = 2MB     ← 共有されている

【PSO（各モデル独立）】
PipelineState × 15個
    ├─ 各1KB × 15 = 15KB

【定数バッファ（各モデル独立）】
ConstantBuffer × 15個
    ├─ 各256B × 15 = 3.75KB
```

**GPU側の総メモリ使用量**: 150KB + 75KB + 2MB + 15KB + 3.75KB = **約2.24MB**

---

#### 最適化の余地

もし **頂点バッファとインデックスバッファも共有** すれば、さらにメモリを節約できます。

```
最適化後のGPU側メモリ使用量:
    VertexBuffer × 1個: 10KB   ← 共有
    IndexBuffer × 1個: 5KB     ← 共有
    Texture: 2MB
    PSO × 15個: 15KB
    ConstantBuffer × 15個: 3.75KB
    合計: 約2.03MB  ← 約210KB削減！
```

**実装方法**: 各 `Model` が同じ `VertexBuffer` と `IndexBuffer` を **参照** するように変更する。

---

### 9.5 PSO（パイプラインステートオブジェクト）の詳細

#### PSOに含まれる情報

```cpp
// PipelineState の作成（簡略版）
D3D12_GRAPHICS_PIPELINE_STATE_DESC psoDesc = {};

// シェーダー
psoDesc.VS = vertexShader;             // 頂点シェーダー
psoDesc.PS = pixelShader;              // ピクセルシェーダー

// レンダーターゲット
psoDesc.NumRenderTargets = 1;
psoDesc.RTVFormats[0] = DXGI_FORMAT_R32_FLOAT;  // シャドウマップ用

// 深度ステンシル
psoDesc.DSVFormat = DXGI_FORMAT_D32_FLOAT;
psoDesc.DepthStencilState.DepthEnable = TRUE;

// ラスタライザー
psoDesc.RasterizerState.CullMode = D3D12_CULL_MODE_BACK;

// ブレンド
psoDesc.BlendState.RenderTarget[0].BlendEnable = FALSE;

// トポロジー
psoDesc.PrimitiveTopologyType = D3D12_PRIMITIVE_TOPOLOGY_TYPE_TRIANGLE;

// ルートシグネチャ
psoDesc.pRootSignature = rootSignature;

// PSOを作成
device->CreateGraphicsPipelineState(&psoDesc, IID_PPV_ARGS(&pso));
```

#### 各モデルが異なるPSOを持つ理由

| モデル | シェーダー | レンダーターゲット | PSO |
|--------|-----------|------------------|-----|
| シャドウマップ用 | `DrawShadowMap.fx` | `R32_FLOAT` (深度のみ) | PSO #1 |
| ZPrepass用 | `ZPrepass.fx` | `R32G32_FLOAT` | PSO #2 |
| G-Buffer用 | `RenderToGBufferFor3DModel.fx` | 5つのG-Buffer | PSO #3 |
| フォワード用 | `sample.fx` (ユーザー指定) | `R32G32B32A32_FLOAT` | PSO #4 |

**これらは全て異なるため、別々のPSOが必要**です。

### 9.6 描画時の流れ

```cpp
// シャドウマップ描画
m_shadowModels[0][0].Draw(rc);
    ↓
    MeshParts::Draw()
        ↓
        rc.SetPipelineState(m_materials[0].m_pipelineState);  // PSO #1 をセット
        rc.SetVertexBuffer(m_meshs[0].m_vertexBuffer);        // 頂点バッファをセット
        rc.SetIndexBuffer(m_meshs[0].m_indexBufferArray[0]);  // インデックスバッファをセット
        rc.DrawIndexed();                                      // 描画


// ZPrepass描画
m_zprepassModel.Draw(rc);
    ↓
    MeshParts::Draw()
        ↓
        rc.SetPipelineState(m_materials[0].m_pipelineState);  // PSO #2 をセット（切り替え）
        rc.SetVertexBuffer(m_meshs[0].m_vertexBuffer);        // 頂点バッファをセット
        rc.SetIndexBuffer(m_meshs[0].m_indexBufferArray[0]);  // インデックスバッファをセット
        rc.DrawIndexed();                                      // 描画


// G-Buffer描画
m_renderToGBufferModel.Draw(rc);
    ↓
    MeshParts::Draw()
        ↓
        rc.SetPipelineState(m_materials[0].m_pipelineState);  // PSO #3 をセット（切り替え）
        rc.SetVertexBuffer(m_meshs[0].m_vertexBuffer);        // 頂点バッファをセット
        rc.SetIndexBuffer(m_meshs[0].m_indexBufferArray[0]);  // インデックスバッファをセット
        rc.DrawIndexed();                                      // 描画
```

**ポイント**: PSO は切り替わるが、**事前に作成済みのPSOを使い回す**ため、オーバーヘッドは小さい。

### 9.7 まとめ：メモリ空間での共有状況

| データ | 共有/独立 | 実装方法 | メモリ空間 |
|--------|----------|---------|----------|
| **TkmFile（頂点・インデックスデータ）** | **共有** | `TResourceBank` で管理 | **CPU側（メインメモリ）** |
| **VertexBuffer（GPU上）** | **独立**（改善の余地あり） | 各モデルが独自に作成 | **GPU側（ビデオメモリ）** |
| **IndexBuffer（GPU上）** | **独立**（改善の余地あり） | 各モデルが独自に作成 | **GPU側（ビデオメモリ）** |
| **Texture** | **共有** | ディスクリプタヒープで共有 | **GPU側（ビデオメモリ）** |
| **PSO** | **独立**（必須） | 各モデルが異なるPSOを保持 | **CPU側（メインメモリ）** |
| **ConstantBuffer** | **独立**（必須） | 各モデルが異なる行列を持つ | **GPU側（ビデオメモリ）** |

#### 実際のメモリ使用量（再計算）

```
【CPU側】
TkmFile（共有）: 16KB
Model インスタンス × 15: 16.5KB
合計: 約32.5KB

【GPU側】
VertexBuffer × 15（独立）: 150KB  ← 最適化可能
IndexBuffer × 15（独立）: 75KB    ← 最適化可能
Texture（共有）: 2MB
PSO × 15（独立）: 15KB
ConstantBuffer × 15（独立）: 3.75KB
合計: 約2.24MB

【総メモリ使用量】
32.5KB + 2.24MB = 約2.27MB
```

### 9.8 最適化の提案

もし、さらにメモリを節約したい場合は、以下のように実装を変更できます：

```cpp
// 最適化版の Model クラス
class Model {
private:
    TkmFile* m_tkmFile;               // 共有
    SharedVertexBuffer* m_vertexBuffer;  // 共有（新規追加）
    SharedIndexBuffer* m_indexBuffer;    // 共有（新規追加）
    MeshParts m_meshParts;            // PSO保持（独立）
    // ...
};
```

これにより、GPU側のメモリ使用量を **約210KB削減** できます。

## 10. 最終結論

### ModelクラスとPSOの関係

- **Modelクラス** = 描画に必要なすべての情報を保持
- **PSO** = `MeshParts` → `Material` の中に保持
- 各モデルが **異なるPSO** を持つことで、**異なるシェーダーで描画可能**

### メモリ共有の仕組み

| データ | 共有方法 | メモリ空間 |
|--------|---------|----------|
| **頂点データ（CPU側）** | `TResourceBank` で共有 | メインメモリ |
| **頂点バッファ（GPU側）** | 現状は独立（最適化可能） | ビデオメモリ |
| **テクスチャ** | ディスクリプタヒープで共有 | ビデオメモリ |
| **PSO** | 各モデルで独立（必須） | メインメモリ |

### パフォーマンスとメモリのトレードオフ

**現在の実装**:
- ✅ 最高のパフォーマンス（PSO切り替えなし）
- ✅ シンプルな実装
- ⚠️ GPU上で頂点データが重複（約210KB）

**最適化版**:
- ✅ メモリ使用量削減
- ❌ 実装が複雑になる
- ✅ パフォーマンスは維持

**結論**: 現代のGPUメモリ（数GB～数十GB）から見ると、210KBの重複は **無視できるレベル** であり、現在の実装で十分実用的です。

ただし、**大量のモデルを扱う場合**（例: 1000体のキャラクター）は、最適化版の実装を検討する価値があります。
